# OPC Agent v1.0.11

本版修掉「更新总是失败、提示旧包仍被占用」的根因：**接手替换文件的交接进程，
自己把 `app.asar` 打开了。**

## 根因

交接脚本由 `OPC Agent.exe` 以 Electron 的 Node 模式启动。Electron 仍然把 asar
支持注入到了 `fs`：脚本只要对 `resources/app.asar` 做一次存在性检查 —— 哪怕只是
问一句「旧包还在吗」—— asar 层就会真的打开这个归档并长期持有句柄。

于是它锁住了自己马上要改名的文件。`rename` 必然 EBUSY，等满 60 秒预算也一样；
Restart Manager 报出来的「持有者」不是用户没关掉的窗口，正是交接进程自己的 pid。

## 修复

- **关闭交接进程的 asar 支持**：脚本一启动、在任何 `fs` 调用之前设
  `process.noAsar = true`，asar 层不再介入；存在性检查从 `existsSync` 换成
  `statSync` 的普通文件判断，stat 也不会再打开归档。

- **等待与重试阶段都复查持有者**：结束判据从「按启动时间」改为「更新开始前就在的
  残留，或确实持有目标文件」。更新开始后才启动、却锁着 `app.asar` 的实例同样会被
  定向结束（依旧只认映像路径在安装目录内的进程，绝不按进程名全局杀）；抢锁重试到
  第 30 / 120 次时再查一次 Restart Manager，定向结束真正的持有者。

- **失败提示能指出持有者是交接进程自身**：这种情况会明说「不是用户窗口没关」，
  不再把用户引去关一个根本关不掉的窗口。`apply-state.json` 的 trace 新增
  `selfHold`、`holdersAtGuard`、`holderRecheck`，事后能区分「用户进程没退」与
  「交接进程自锁」。

## 校验

- `verify:a176-update-swap` **151 条全过**，新增三组断言：交接进程自身持有目标文件
  时不得静默通过、持有者启动晚于更新开始也要定向结束、进程已退出但文件仍被占用时
  继续重试。全部用假时钟与假进程表，不真等预算。

- `verify:a171-update` **195 条全过**。

## 需要注意

- **1.0.10 及更早版本仍带旧交接脚本**：修复只对本版内置的脚本生效。所以从 1.0.10
  或更早升级时，应用内自动替换仍可能失败一次；请先按下面的方式手动升到本版。

- 下一次真正的「应用内自动更新」要等 1.0.12 发布后才能被真实验证。

## 升级方式

- **1.0.10 / 1.0.9**：建议手动升一次 —— 完全退出应用（托盘退出，任务管理器确认
  没有 `OPC Agent` 进程），用本 Release 的 `OPC-Agent-1.0.11-x64-full.zip` 解压覆盖
  安装目录；也可以只把 `resources/app.asar` 换成 Release 里的 `app-1.0.11.asar`
  （更省流量）。

- **1.0.8 及更早（含 1.0.7、1.0.6、1.0.5）**：同上，手动覆盖安装目录。

- **1.0.0 旧版**：内置公钥与当前签名不匹配，需先手动更新一次。

- 会话数据保存在 `%APPDATA%\opc-agent`，覆盖安装不受影响。
